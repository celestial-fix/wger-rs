## Open issues and the agent's planned fixes (from its last notes, lines 1568-1581)

1. **JWT signing fails in the JWK-to-PKCS8 conversion** (causes failures 7-12). The key
   parses, but jsonwebtoken rejects the DER (`InvalidEncoding`). The agent's diagnosis:
   `rsa::RsaPrivateKey::from_components` leaves out the CRT coefficients. Planned fix: call
   `key.precompute()` (and/or `key.validate()`) before `to_pkcs8_der()`, or switch to
   `to_pkcs8_pem` / `to_pkcs1_pem`. It had found `precompute` at `rsa-0.9.10/src/key.rs:330`.
   Not applied.
2. **An invalid token should return 403, not 401** (failures 4 and 5). Planned fix: an axum
   middleware that authenticates any request carrying an `Authorization` header before
   the handler runs, so invalid credentials get 403 even on public routes like `/version/`.
   The invalid-bearer body should match simplejwt exactly ("Token is invalid", not
   "Token is invalid or expired"). Not applied.
3. **ORDER BY alias double-qualification from chained `str::replace`.** The default
   orderings became `l.l.datetime` / `l.l.id` (nutrition diary) and `m.m.date` / `m.m.id`
   (weight entries), which Postgres rejects with "invalid reference to FROM-clause entry
   for table l/m". **Fixed in this tree**: `httpx::prefix_bare` (lines 1538-1559) replaces
   whole tokens only and returns already-qualified strings unchanged. It's used in
   `api/nutrition.rs` and `api/other.rs`. The 94/12 run shows no remaining l/m 500s. The
   agent also meant to check meal ordering for the same pattern and hadn't confirmed it.
4. **Trophy progress returns 8 items, Django 9** (failure 3). Not investigated yet. The next
   step was to curl Django and diff the trophy IDs.
5. **Ingredient approximate count and empty page** (failure 2). Django's
   `ApproximateCountManager` reads `pg_class.reltuples`, which is -1 on an unanalysed
   table, for the unfiltered list. DRF `LimitOffsetPagination` then returns an empty page
   because offset > count. Planned fix: port the reltuples count (cast to i64, keeping -1)
   and make `httpx::paginated` return an empty `results` whenever offset > count, on all
   endpoints. Filtered and search counts stay exact.
6. **Repetition-unit ordering** (failure 1). Planned fix: `ORDER BY unit_type, name`. The
   agent also said it would check the `Meta.ordering` of other lookups (license is
   `full_name`, weight unit is `name`).
7. **A non-integer path id should return 404, not 400** (failure 6). Planned fix: a custom
   `Pk` extractor that replaces every `Path<i32>`, including nested routes like
   `routine/:id/structure`, and turns parse failures into 404. UUID and media `Path<String>`
   routes stay as they are. The agent also considered explicit `/exercise/search` and
   `/ingredient/search` 404 routes as a smaller fallback.
8. **Refresh-token compatibility** (failures 9 and 10). The 500 shows Rust accepts Django's
   RS256 refresh tokens (same key, same shape). Once signing works, Rust should rotate them,
   so phones wouldn't need to log in again at cutover. The agent planned to change the
   "rust rejects django refresh" check so that 200 means compatible and 400 means a cutover
   re-login is needed, with neither counted as a failure. The module docs in `src/auth.rs`
   still say a re-login is needed.
9. **Login password-hash upgrade.** The agent noted that Rust login doesn't upgrade
   pbkdf2 to argon2 the way Django does. It decided no reseed was needed because Django had
   already upgraded the seeded user and Rust verifies argon2.
10. **Still to do for M1 (per the brief)**: get the harness to 0 failures, commit on a
    branch, push, and open a PR to main (never main itself, no merge or force-push). None of
    this happened on the VM.
